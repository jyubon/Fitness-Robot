# Fitness Robot – Full-Stack Architecture & Data Models

All data is **real** (from Raspberry Pi + ESP32 + watch). No dummy data is generated by the system.

---

## 1. System Overview

```
┌─────────────────────────────────────────────────────────────────┐
│                        Raspberry Pi 4                           │
│  person_raspi.py (MediaPipe)                                    │
│    • Pose/Hand detection per exercise                           │
│    • Real-time publishing (HTTP) → Backend                      │
│    • Control listener (WS) ← Backend (force_stop / switch_mode) │
│    • UDP commands → ESP32                                       │
└─────────────────────────────────────────────────────────────────┘
                               │
                               │ HTTPS (JWT) + WS
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│                        FastAPI Backend                          │
│  • Auth (JWT)                                                   │
│  • REST: sessions, events, watch, analytics, control            │
│  • WS: /ws/telemetry (Pi + Browsers), /ws/control (bidir)       │
│  • MongoDB (Motor async)                                        │
└─────────────────────────────────────────────────────────────────┘
                               │
                               │ WS broadcast (per user)
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│                     Web Dashboard (Browser)                     │
│  • Live Telemetry (reps, plank, form, robot state, watch)       │
│  • Remote Control (force stop, mode switch)                     │
│  • Analytics (weekly aggregates + history)                      │
│  • MJPEG camera stream (optional)                               │
└─────────────────────────────────────────────────────────────────┘
```

## 2. Core Components

### 2.1 Pi (person_raspi.py)
**Publishing helpers (HTTP, fire-and-forget):**
- `publish_session_start(exercise_type)`
- `publish_session_end(summary_dict)`
- `publish_rep(exercise, set_num?, count?, left?, right?, ...)`
- `publish_set_complete(exercise, set_num, reps)`
- `publish_form_error(message, side=None)`
- `publish_robot_state(state, command=None)`
- `publish_plank_time(value_seconds)`
- `publish_pause()` / `publish_resume()`

**Control listener (background WS):**
- Subscribes to `/ws/control?token=...`
- Handles `force_stop` and `switch_mode`

**Session timing (accurate active vs total):**
- `_session_start_wall`, `_pause_accumulator`
- `publish_session_end` computes:
  - `total_duration_s = now - _session_start_wall`
  - `active_duration_s = total - _pause_accumulator`

### 2.2 Backend (FastAPI + Mongo)

**Routers / Endpoints:**
- `POST /auth/register`, `POST /auth/login`
- `POST /api/sessions/start` → returns `{ session_id }`
- `POST /api/sessions/end`
- `POST /api/events` (generic telemetry sink)
- `POST /api/watch/steps` (BLE watch)
- `GET  /api/analytics/weekly`
- `POST /api/control` (UI → Pi)
- `WS   /ws/telemetry?token=...`
- `WS   /ws/control?token=...`

**WebSocket Manager (`ws_manager.py`):**
- Per-user sets:
  - `telemetry_connections[user_id]`
  - `control_connections[user_id]`
- Broadcast helpers for both channels

**Auth (`auth.py`):**
- JWT (HS256) with `sub = user_id`
- Bcrypt password hashing
- `get_current_user_id(token_or_dep)` → user_id str

### 2.3 Frontend (Vanilla + Tailwind + Chart.js)
- Auth view → stores JWT + user_id in localStorage
- Live view:
  - Robot state pill, current workout/set/reps, plank timer
  - Watch steps + extras
  - Mode switch buttons (HTTP → /api/control)
  - Force Stop (global)
  - Form/encouragement log (real-time)
  - MJPEG camera (user-provided URL)
- Analytics view:
  - 4 KPIs (reps, plank, steps, form %)
  - Reps bar chart (curls/push/squats)
  - Active vs Total time line
  - Form doughnut
  - Session history list

## 4. API & WebSocket Contracts

### REST (all require `Authorization: Bearer <JWT>`)

- `POST /api/sessions/start` → `201 { "session_id": "..." }`
- `POST /api/sessions/end` → `200 { "ok": true, "session_id": "..." }`
- `POST /api/events` → `201 { "event_id": "..." }`
- `POST /api/watch/steps` → `200 { "ok": true }`
- `GET  /api/analytics/weekly` → weekly aggregates + history
- `POST /api/control` → `202 { "ok": true, "action": "...", "mode": "..." }`

### WebSocket

- `/ws/telemetry?token=...`
  - Server → Client: live events (broadcast from Pi + backend)
  - Client → Server: (optional acks; Pi mostly producer)

- `/ws/control?token=...`
  - Bidirectional:
    - UI → Pi: `{ "action": "force_stop" }` or `{ "action": "switch_mode", "mode": "SQUATS" }`
    - Pi → UI: raw acks / echoes

**Broadcast format (from backend):**
```json
{ "type": "rep", "event_id": "...", "ts": "...", "payload": { ... } }
```

## 5. Data Flow

### Exercise Session (example: Squats)
1. Pi: positioning → `positioning_completed = True`
2. Pi: `publish_session_start("squats")` → `POST /api/sessions/start`
3. Backend: insert `sessions` doc, broadcast `session_start` via WS
4. Pi: on each good rep → `publish_rep("squats", set_num, count)`
5. Backend: insert `events`, broadcast `rep`
6. Pi: set ends → `publish_set_complete(...)`
7. Pi: session ends → `publish_session_end(summary)`
8. Backend: update `sessions`, broadcast `session_end`

### Pause/Resume
- Thumbs-up detected → `publish_pause()` / `publish_resume()`
- Pi tracks `_pause_accumulator`
- `publish_session_end` uses it for `active_duration_s`

### Watch Steps
- BLE page / future listener → `POST /api/watch/steps`
- Backend upserts:
  - `watch_data` (raw)
  - `daily_aggregates` (steps + last_watch_sync)
- Broadcast `watch_steps`

### Control (UI → Pi)
1. Browser: `POST /api/control { action, mode }`
2. Backend: `ws_manager.broadcast_control_to_user(...)`
3. Pi control listener receives → `force_stop.set()` or queue switch

## 6. Analytics & Aggregation Strategy

**Current state (as-built):**
- `daily_aggregates` only receives **steps** from watch endpoint.
- `reps`, `plank_time_s`, `form_*` fields exist in the model but are **not populated** from Pi data today.

**Recommended enhancement (to make /weekly work fully):**
Option A (lightweight, recommended):
- On `POST /api/events`, have a small aggregator:
  - If `type == "rep"` → increment `daily_aggregates.reps[exercise]`
  - If `type == "plank_time"` → add delta to `plank_time_s` (or set max)
  - If `type == "form_error"` → increment `form_flaw_count`
- Also increment `form_good_count` on "rep" events that have no recent form_error (simple heuristic).

Option B (explicit):
- Add `publish_daily_rollup(...)` calls from Pi at session end.
- Or a nightly aggregation job.

**Analytics response shape (current):**
```json
{
  "user_id": "...",
  "from_date": "...",
  "to_date": "...",
  "totals": { "steps": N, "reps": { "bicep_curls": M, ... }, "plank_time_s": P },
  "daily": [ { "date": "...", "steps": , "reps": {}, "plank_time_s": , "form_good": , "form_flawed": } , ... ],
  "form_accuracy": { "good": G, "flawed": F },
  "session_history": [ { id, exercise_type, started_at, ended_at, active_duration_s, summary }, ... ]
}
```

## 7. Auth & Security Notes

- JWT only (no sessions).
- All REST + WS require token.
- Pi uses token from env (`BACKEND_TOKEN`).
- CORS currently wide (`*`); tighten for production.
- Passwords: bcrypt via passlib.
- Secrets: `JWT_SECRET` in env (never commit).

## 8. Known Gaps / Future Work

1. **Daily aggregates from exercise data**
   - `reps`, `plank_time_s`, form counts are not updated from Pi events today.
   - Implement lightweight aggregator in `POST /api/events` or explicit rollup calls.

2. **Form accuracy heuristic**
   - Current analytics counts form errors as "flawed".
   - Consider counting "rep" events without nearby form_error as "good".

3. **Active time for plank**
   - Plank uses continuous `publish_plank_time`, not start/end.
   - Consider a "plank_session" concept or derive active time from time deltas.

4. **Per-set timing / rest**
   - Currently only tracked in Pi memory; not persisted except via session summary.

5. **Camera stream auth**
   - MJPEG URL is user-provided; no auth proxy today.

6. **Multi-device Pi**
   - Current design assumes one Pi per user. If multiple, add `device_id`.
